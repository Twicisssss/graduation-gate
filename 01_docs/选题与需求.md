# 选题与需求（题目原文 + 我的解读）

> 来源：毕业设计选题管理平台（电子与电气工程学院 · 通信工程 · 2027 届）
> 题目：**多重验证门禁系统研究与设计**　教师：刘文琮　来源：科研项目　方向：信息通信　难度：中　可指导人数：1　拟完成周期：10–12 周　预期成果：制作实物

---

## 一、题目要求做什么

技术路线分五步：需求分析与因子选型 → 级联策略设计 → 硬件集成与原型搭建 → 软件后台与日志管理 → 功能测试与模拟攻击验证。

1. **三因子选型**：PIN（知识）+ RFID/NFC（持有物）+ 指纹/人脸（生物特征）。题目明确指纹模块（AS608/FPM10A）成本低、SDK 成熟，适合本科生；RFID（RC522）作为持有物因子的入门选择。
2. **级联验证**：不是简单叠加，而是"第一因子响应最快作为触发条件 → 第二因子在限定时间内输入 → 第三因子作为最终决策"，任一失败或超时即锁定并记录。
3. **硬件集成**：读卡、指纹、键盘、电磁锁、蜂鸣器与指示灯集成；重点是**电源管理与电平匹配**（电磁锁瞬时电流大，需独立供电或继电器隔离，避免主控复位）。
4. **后台与日志**：记录每次验证的时间、因子类型、结果与失败原因；支持用户注册（录卡 ID 与指纹模板）与权限分级。
5. **攻防测试**：正常通行耗时、单因子失效拒绝、复制卡攻击、暴力尝试锁定——这是毕业设计区别于课程设计的关键环节。

## 二、题目给的三个创新点（论文可直接展开）

| 编号 | 名称 | 一句话 |
| --- | --- | --- |
| 创新一 | 基于时序绑定的级联验证 | 前序因子通过后，后续因子仅在限定时间窗（10 s）内有效；把"持有物 + 知识 + 生物特征"在时间维度耦合 |
| 创新二 | 低成本"补偿性"多因子架构 | 承认 Mifare 卡可克隆，把它定位为第一层筛选而非安全边界，安全边界放在 PIN + 指纹 |
| 创新三 | 异常尝试行为检测 | 同一卡/终端连续 3 次失败 → 锁卡 + 日志高亮 + 蜂鸣器长鸣，让系统从"被动验证"具备主动感知 |

## 三、关键决策记录

### 决策 1：主控用 STM32F103C8T6，不用 ESP32 / 树莓派

题目建议"ESP32 或树莓派"，但本设计选 STM32，理由：

- **时序可控**：三因子窗口要求毫秒级、可预测的响应；ESP32 的 Wi-Fi 协议栈会抢占时序，树莓派有系统调度抖动。
- **不与网络耦合**：日志走 USB 串口直连 PC，主控只负责实时认证，联网问题不进入关键路径。
- **已有积累**：智能循迹小车、摇杆云台、智能门锁均为 STM32/STC8H 平台，10–12 周内风险最低。

### 决策 2：存储用内部 Flash，不用 AT24C02

- AT24C02 只有 **256 字节**，用户记录按 16 字节算只能存 16 条，日志无处安放。
- 改用 STM32 内部 Flash 模拟 EEPROM（1 KB/页），够存 60 条日志，且省掉一路 I²C、避免与读卡器射频干扰。
- 掉电安全：先写新页再切换指针，避免擦除中途掉电丢数据。

### 决策 3：锁体用 12 V 电磁锁（断电开锁），不用舵机模拟

- 舵机"嗒"一下更像玩具；电磁锁有真实门禁的机械感与电流冲击，答辩演示更有说服力。
- **断电开锁（fail-safe）**符合消防疏散逻辑，是论文里可以写一句"安全设计"的点。
- 代价：必须做电源隔离与续流保护——这恰好是题目第三阶段点名的"关键任务"。

### 决策 4：后台用本地 Python 服务 + 浏览器面板，不上云

- 题目允许"简化为一端运行在 PC 上的 Python GUI 或 Web 页面"。
- 用浏览器面板而非桌面 GUI：表格、图表、导出是 Web 的强项，而且已有前端经验能做出"审计系统"的样子，论文里能放真实截图。
- 用**本地标准库服务**而非云数据库：一条命令启动，断网可用，答辩现场零依赖。
- 设计上**密码只存哈希、不提供"查看明文"功能**，作为论文"安全设计"小节的正面案例。

### 决策 5：不接公网、不用蓝牙，日志走 USB 串口

- 题目不要求公网。任务书原文允许后端"简化为一端运行在 PC 上"。
- 蓝牙只解决 10 米内的线缆，不解决联网：数据最多到那台手机，且要多写一个 App，故障点从 1 个变 3 个。
- 经典蓝牙 SPP（HC-05）在 macOS 上常不生成串口设备，在 iPhone 上完全不支持；改 BLE 又要额外客户端。
- 结论：**USB 串口是风险评估后成本最低、演示最稳的方案**。省下的 3–4 天投到攻防测试与参数整定上，对分数更有价值。
- 答辩话术：「考虑到现场网络与配对的不确定性，采用本地直连保证演示可靠性，远程上报作为可扩展能力预留。」——这是工程取舍，不是偷懒。

### 决策 6：开发机分工 —— Mac 写文档，Windows 跑开发

- 本机（MacBook）只做文本编辑与图表生成：Markdown、Word、Python 画图。
- 开发（Keil MDK、STM32CubeMX、串口调试、烧录）全部在另一台 Windows 电脑上完成。
- 因此仓库必须两端可用：代码与工程目录用 ASCII 命名，换行由 `.gitattributes` 统一，文档里给出的串口示例同时写 `COM3` 与 `/dev/tty.*`。
- 同步方式：两端 `git pull` → 改 → `git commit` → `git push`，只通过仓库交换文件，不用 U 盘拷贝。

## 四、验收口径（自己对着打分）

| 老师会问 | 要能拿出 |
| --- | --- |
| 三重验证怎么保证顺序？ | 状态机图 + 超时被执行的现象 |
| 卡能复制，安全性在哪？ | 分层信任论证 + 复制卡测试结果 |
| 怎么证明比单因子好？ | 单/双/三因子各 10 次的通过率与耗时对比 |
| 出问题怎么追溯？ | 后台日志界面 + 日志条数守恒验证 |

分数直觉（经验判断，非官方标准）：功能跑通 ≈ 及格线；加时序绑定 + 攻防测试 ≈ 良好；再加后台审计 + 参数整定实验 + 权衡论证 ≈ 优秀。
